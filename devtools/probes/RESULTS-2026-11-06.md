Run 2026-11-06 on 1.5.0, one launch (`lab start --menu`, run folder `~/.tower-bench/runs/2026-11-06T12-25-10`), the
usual mod set plus the probe mod built by [build-probe-mod.py](build-probe-mod.py). The human was Amina, seed 4242

## Probe 1: a copied ability bullet on another leader

Watched. A trait of our own on Amina (`TRAIT_LSHUF_PROBE_AMINA`) carrying Pachacuti's
`PACHACUTI_MOD_CITY_PRODUCTION_FROM_FOOD` gave her capital +0.5 Production from 5 Food (5 to 5.5) on turn 1. The city's
Production breakdown (`city.Yields.getYields()`) lists the line as "Earth Shaker", Pachacuti's ability name. The
modifier's `Tooltip` argument (`LOC_TRAIT_LEADER_PACHACUTI_ABILITY_NAME`) names it, so a moved bullet keeps its source
leader's name in breakdowns unless the mod copies the modifier under a new id with its own `Tooltip`.

The description assembled in SQL (Amina's text with its `[/BLIST]` dropped, then Pachacuti's text from its third `[LI]`)
drew as a fourth bullet with its icons on the Civilopedia page and the diplomacy panel
(`p8-civilopedia-amina.png`, `p8-diplomacy-amina.png`).

## Probe 7: keeping the human's leader

Watched. The game config was written from the main menu after Play Now's reset and before `startGame`; each criterion
had its own action group inserting a tag into a probe table.

| Criterion | Config value | Result |
| --- | --- | --- |
| `LeaderPlayable` `LEADER_X`, 38 leaders | (none) | All 38 applied, including the 32 not in the game; `LEADER_NOPE` didn't |
| `LeaderPlayable` `StandardLeaders::LEADER_X` | (none) | None applied |
| `ConfigurationValueMatches` value `1` | key set to the number `1` | Didn't apply |
| `ConfigurationValueMatches` value `1` | key set to the string `"1"` | Applied |
| `ConfigurationValueMatches` value `1` | key never set | Didn't apply |
| `ConfigurationValueContains` value `LEADER_AMINA` | key set to `["LEADER_AMINA","LEADER_PACHACUTI"]` | Applied |
| `ConfigurationValueContains` value `LEADER_NOPE` | the same list | Didn't apply |
| `ConfigurationValueContains` value `LEADER_AMINA` | key set to `"LEADER_AMINA,LEADER_PACHACUTI"` | Applied |
| `ConfigurationValueContains` value `1,2,3` | key set to `"1"` | Applied |
| `ConfigurationValueContains` value `2,3` | key set to `"1"` | Didn't apply |
| `ConfigurationValueContains` value `1,2,3` | key set to the number `1` | Didn't apply |

- `LeaderPlayable` matches a leader that's available to play, not one that's in this game, so it can't find the
  human's leader. It may gate rows on a DLC leader being owned; that's unwatched without a DLC removed.
- Both criteria compare text. A key set as a number never matches.
- The per-leader string key (`LShufKeep_<LEADER> = "1"` with `ConfigurationValueMatches`) works and is the route for
  Your leader: As chosen. `ConfigurationValueContains` on a list key also works, but these results don't tell a whole
  entry from a substring (`LEADER_XERXES` in a list holding `LEADER_XERXES_ALT`), so the per-leader key is the safe one.
- `GameSetup.setPlayerParameterValue(0, "PlayerLeader", ...)` sent in the same call as `Configuration.editGame().reset`
  returned 5 and left `RANDOM`; sent again a moment later it returned 0 and took.

### Probe 11 follow-up: the same format as the game's rows

Watched the same day (run `2026-11-06T13-33-17`, same setup). A row with no child lines hides its expand arrow, which
shifts its value right of the rows that have one, so the named line now carries one child row naming its source, as
"From Buildings" carries "Palace". The step's `id` doesn't lead to its modifier (`GameInfo.Modifiers.lookup(268)` was
an unrelated memento modifier; `GameEffects.getModifierDefinition*` returned null), so the wrap finds the source from
data instead: modifiers whose `Tooltip` composes to the step's name, with a `FromYieldType`, a `ToYieldType` equal to
this yield, and a `Percent` equal to the multiplier inside the step. One match gives a child row (the source yield's
name through `Locale.stylize`, the percent with `GameValueDisplayTypes.PERCENTAGE`); none or several give no child row.

The breakdown read "Warrior-Queen of Zazzau +0.5" with the expand arrow, its value lined up with "From Buildings +5",
and the child "Food +10%" with the Food icon (`p11-city-details-named-formatted.png`). The match found one modifier,
`LSHUF_LEADER_AMINA_PACHACUTI_PROD_FROM_FOOD`. The game's JS engine rejected `??` mixed with `&&` without parentheses
(`SyntaxError: Unexpected token '&&'` in UI.log) although `node --check` passed it; the build's lint should catch it.

## Probe 12: what the setup screen can learn about another mod

Watched the same day at the main menu (run `2026-11-06T14-48-43`, no game started, usual mod set).

- `Modding.getInstalledMods()` gives `handle`, `id`, `enabled`, `name`, `description`, `created` (empty for every mod
  read), `allowance`, `official`, `source`, `sourceFileName`, `subscriptionType` (`OfficialContent`,
  `SteamWorkshopContent`, `CommunityContent`) and `subscriptionId` (the Workshop id). No version, no update time.
- `Modding.getModProperty(handle, "Version")` returns the modinfo's `<Version>` property when it has one (Tower
  Settings Keeper `1.3.0`, Settlement Limit Settings `1.0.2`) and `null` when it doesn't (Aging Warehouses).
  `LastUpdated`, `Timestamp`, `Created` and `Updated` were `null`. None of the 25 listed leader mods sets `<Version>`, so
  a version pin can't work for them.
- `fetch` isn't defined in the game's UI. `XMLHttpRequest` on `fs://game/<mod id>/<sourceFileName>` returned the other
  mod's whole modinfo (Settlement Limit Settings, 49,842 bytes, status 200), and `fs://game/<mod id>/<path>` returned its
  script files (status 200). The mod id in the path counts: a file asked for under another mod's id, or a made-up id,
  returned 404. A disabled mod's files read the same way.

So at setup our script can read, live, what each leader mod loads, with no list to keep current.

## Probe 13: the leader accordions

Watched the same day (run `2026-11-06T15-02-34`, probe mod [lshuf-probe-accordion](lshuf-probe-accordion/) built by
[build-accordion-probe.py](build-accordion-probe.py), usual mod set). Four setup parameters in the `AdvancedOptions`
group: two leader accordions (array `Select`, `UxHint = 'InvertSelection'`, 38 base and DLC leaders from the frontend
`Leaders` table), one storing `|LEADER_X|` and one storing plain `LEADER_X`; an "Include modded leaders" `bool`; and a
modded accordion with two base leaders standing in, behind a `ParameterDependencies` row on the check box.

- **Registered as accordions.** `GameSetup.findGameParameter` gave both leader parameters `array: true`, `hidden:
  false`, 38 values and `uxHint` `InvertSelection`: the shape `advanced-options.js` draws with
  `AdvancedOptionMultiselectField` inside `AdvancedOptionsAccordian`, as for Victories and Crises.
- **The modded accordion follows its check box.** With the box off, `findGameParameter("LShufModdedIn")` returned
  nothing; after `setGameParameterValue("LShufIncludeModded", true)` it existed, not hidden, with its two values.
- **The stored lists.** `setGameParameterValue` with an array stored it as given: `LShufExcludedLeaders` =
  `["|LEADER_XERXES|","|LEADER_AMINA|"]`, `LShufExcludedLeadersPlain` = `["LEADER_XERXES","LEADER_AMINA"]`,
  `LShufExcludedModdedLeaders` = `["|LEADER_PACHACUTI|"]`, `LShufIncludeModded` = `true`.
- **The per-leader rules in the game.** Applied: `MK:LEADER_XERXES`, `MK:LEADER_AMINA`, `PL:LEADER_XERXES`,
  `PL:LEADER_AMINA`, `MD:LEADER_PACHACUTI`, and the check box matched with both `<Value>1</Value>` and `true`. Not
  applied: `LEADER_XERXES_ALT` in either list, every other leader, and the modded stand-in left on (Amina). The plain list
  doesn't test the risky direction (a list holding only `LEADER_XERXES_ALT`, checked for `LEADER_XERXES`); the `|...|`
  markers rule that out either way, so the build keeps them.

Not watched: the accordion drawn on screen. Opening the advanced options popup from script failed: the create-game
screen's buttons are ui-next `Activatable`s, and `engine-input` events (`mousebutton-left`, START then FINISH) moved the
flow from leader select to the hub but didn't open the `advanced-options` popup, and window captures of the shell kept
showing a stale frame. A person opening New Game, then Advanced Settings, with the probe mod on settles it in a minute.
